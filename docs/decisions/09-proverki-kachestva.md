# Проверки качества

**Решение.** Четыре независимые проверки поверх обычной сборки: состав зависимостей, файлы
репозитория, собранные манифесты, собранные образы. Плюс SonarQube по коду и страницам
и коллекция запросов к работающей системе. Принятые риски записаны с обоснованием и сроком.

## Почему так

**Перечень состава строит сборка, а не читается из файла с зафиксированными версиями.** Такой
файл забывают обновить, и проверка идёт по устаревшему списку; перечень, который вычисляется
заново при каждом запуске, устареть не может.

**Отчёт отдельно, ворота отдельно.** Сначала пишется полный отчёт — с находками любой важности
и с подавленными, — и только потом проверяется, не осталось ли в нём серьёзного. Иначе «зелено»
неотличимо от «зелено, потому что всё подавлено».

**Версии из спецификаций зависимостей не переопределяются.** Даже когда исправленная версия уже
вышла: переопределение вынимает одну библиотеку из проверенного набора и делает сборку не тем,
что выпускали её авторы. Вместо этого разбирается, достижим ли уязвимый путь, и решение
записывается с датой, после которой находка снова роняет проверку.

**С образами наоборот.** Там уязвимости приходят из пакетов базового слоя и лечатся пересборкой,
поэтому ворота по образам роняют сборку на всём, для чего исправление существует. То, чего
починить нечем, ворота не роняет — красная проверка, которую нельзя починить, перестаёт
что-либо значить.

**Проверяются собранные манифесты, а не значения по умолчанию.** Разница существенная: половина
находок относится к тому, что получилось после подстановки наших значений в чужие чарты.

**Наборы правил для своего и чужого разные.** Свои рабочие нагрузки проходят полный набор;
у чужих чартов исключены два правила о том, как их образы запускаются внутри, — через значения
это не задаётся, а править чужие шаблоны означало бы проверять каждый компонент заново.
Всё, что задаётся значениями, приведено в порядок.

**Trivy не отдаёт результаты в Sonar.** Разные вопросы: Sonar отвечает «хорошо ли написан наш
код», Trivy — «что известно плохого про чужой код, который мы используем». Sonar получает от
чужих библиотек только classpath, и только чтобы разбирать типы в нашем коде.

## Что нашлось

Проверки оправдали себя находками, которых не видно в коде: у хранилища в кластере не было
пределов ресурсов вовсе, у Grafana была роль уровня кластера с правом читать секреты, описание
realm с секретами клиентов лежало в карте настроек, у образа страниц базовый слой отстал
на десяток исправимых уязвимостей, а в коде — незакрытый архив при отказе разбора и потерянный
откат при ошибке ввода-вывода во время загрузки файла.

## Последствия

- `tools/scan.sh` требует собранных образов для последнего шага и поднятого Docker.
- SonarQube поднимается рядом на время прогона (`tools/sonar/compose.yaml`) и вместе со стендом
  в память машины разработки не помещается — их запускают по очереди.
- Коллекции запросов нужны учётные записи и клиенты, существующие только на стенде; они описаны
  в realm и в рабочем окружении не создаются.
