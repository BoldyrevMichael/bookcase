# bookcase

Личное хранилище электронных книг. Файлы загружаются как есть — с непонятными именами и без метаданных;
система сама разбирает формат, извлекает автора, название и год, приводит их к единому виду и складывает
книгу в каталог, по которому можно искать, отбирать и скачивать под аккуратным именем.

Библиотека личная: пользователь видит только свои книги, чужих не существует ни в поиске, ни по прямой ссылке.

## Из чего состоит

| Сервис | За что отвечает |
|---|---|
| `catalog` | карточки книг, авторы, темы, поиск, подборки, права владельца |
| `storage` | файлы: приём потоком, хранение, выдача, сборка архивов |
| `ingester` | разбор загруженного файла и извлечение метаданных |
| `enricher` | уточнение метаданных и обложек по внешним источникам |

Снаружи стоит шлюз на Gateway API, вход — через Keycloak. Браузер работает по сессионной cookie,
программные клиенты — по токену; сами сервисы в обоих случаях проверяют токен самостоятельно.

## Стек

Java 25, Spring Boot 4.1, Gradle 9.7. Хранение — PostgreSQL и SeaweedFS, обмен сообщениями — Kafka,
наблюдаемость — Actuator, Micrometer, Prometheus и Grafana. Развёртывание — Helm в Kubernetes.

Версии всех зависимостей собраны в `gradle/libs.versions.toml`. То, чем управляет спецификация
зависимостей Spring Boot, там не дублируется.

## Сборка

```bash
./gradlew check          # формат, компиляция, тесты, checkstyle, SpotBugs с FindSecBugs, покрытие
./gradlew spotlessApply  # привести раскладку кода в порядок
./gradlew assemble       # исполняемые архивы всех сервисов
./gradlew sbom           # перечень состава для проверки уязвимостей
```

Общие настройки сборки лежат в `build-logic` — три соглашения (`java`, `quality`, `service`),
которые модули подключают одной строкой. Настройки анализаторов — в `config/`.

В `shared/` живёт то, что обязано быть одинаковым во всех сервисах: `shared/security` —
проверка токена (подпись, издатель, получатель, срок), `shared/events` — описания событий,
которые один сервис отправляет, а другой читает, `shared/metadata` — приведение значений
к общему виду (язык из «eng» и «Russian» в «en» и «ru»). Расхождение в проверке токена было бы
не разнобоем в стиле, а дырой, поэтому настройка приезжает к сервису готовой.

## Как разложены книги

Три разные вещи, путать которые дорого:

- **тема** отвечает на вопрос «о чём книга»; тем у книги несколько, словарь плоский и растёт
  по мере надобности — при вводе подсказываются уже заведённые;
- **подборка** отвечает на вопрос «зачем собраны вместе»: «к экзамену», «есть на бумаге»;
- **полка** — состояние чтения, у книги ровно одно значение.

Отдельного списка личных пометок нет: полка, подборки и избранное закрывают их целиком,
а вторая сущность меток заставляла бы каждый раз выбирать, куда писать очередное слово.

Иерархии у тем нет намеренно. Книга обычно про несколько тем сразу, а дерево предполагает
одно место; кроме того, перечень тем с числами считается одним запросом и не требует ответа
на вопрос, входят ли книги ветки в счётчик её корня. Понадобится иерархия — добавится поле
«родитель», не ломая данных; обратный ход дороже.

## Уточнение метаданных

Из файла и его имени извлекается далеко не всё: у сканов в DJVU метаданных нет вовсе, а у книг
с непонятными именами не набирается даже названия. Недостающее дополняется из внешних справочников —
`enricher` единственный, кто ходит в интернет.

Справочников два, и спрашиваются они по очереди, потому что сильны в разном. **Google Books** знает
русские издания, которых больше нет нигде, но требует бесплатного ключа: без ключа запросы уходят
в общую безымянную квоту, а она всегда уже исчерпана. **Open Library** ключа не требует, данные под
CC0, и она находит то, о чём Google молчит. Без ключа первый справочник просто выключается, и
библиотека работает на втором; при полностью недоступной сети — работает как ни в чём не бывало,
книги просто остаются с тем, что дал файл.

Ключ кладётся в `deploy/compose/.env` переменной `GOOGLE_BOOKS_API_KEY`; как его получить, написано
в `.env.example`.

**Найденное проверяется, а не записывается сразу.** Справочник отвечает тем, что счёл похожим, и это
регулярно другая книга: на файл `4be534.pdf` предлагается «Мастер и Маргарита», на `2252.pdf` — том
договоров ООН. Кандидат принимается, только если совпал ISBN либо сошлись название и автор:
названия сравниваются по значимым словам, совпадение по одному числу совпадением не считается,
а разные авторы при похожем названии — признак чужой книги. Непринятый кандидат оставляет книгу как
была; принятый по ошибке испортил бы карточку молча, и владелец этого не заметил бы.

**Пишется только в свободные места.** У каждого поля карточки хранится происхождение
(`EMBEDDED → FILENAME → EXTERNAL → USER`): вычитанное из самого файла и исправленное человеком
уточнение не трогает, угаданное из имени — уточняет. Год дописывается лишь в пустое поле: справочники
систематически отдают последнее переиздание, тогда как у владельца лежит то издание, что записано
в имени файла.

**Обложки хранятся у себя, а не ссылками на чужой сайт.** Уточнитель забирает картинку и отдаёт её
хранилищу; в карточке остаётся только хэш, по которому обложка потом и запрашивается. Ссылка на
чужой сайт означала бы, что браузер владельца ходит к справочнику при каждом показе списка, а сама
картинка однажды пропадёт.

Обложка запрашивается по карточке — `GET /api/v1/books/{id}/cover`, — и каталог сначала проверяет,
чья это книга. Наружу отдаётся только признак `hasCover`; хэш обложки клиенту не показывается и
прямого адреса в хранилище у него нет — этот маршрут шлюзом не выставлен вовсе, обложку забирает
каталог изнутри сети.

Так сделано не из перестраховки. Имя объекта в хранилище — хэш содержимого, и посчитать его может
кто угодно, скачав ту же картинку у справочника. Будь адрес доступен снаружи, ответ «есть» или
«нет» сообщал бы, лежит ли книга в библиотеке, — а сервис устроен ровно наоборот: на чужую книгу он
отвечает 404, чтобы не подтверждать даже факт её существования. Показу в браузере это не мешает:
страница открыта по сессионной cookie, и тег изображения отправляет её сам.

Класть обложки может только уточнитель — у него для этого своя учётная запись в Keycloak с
единственной ролью `covers-writer`; пользовательского токена в фоне нет и быть не может. Роль
нужна сверх входа потому, что у обложки нет владельца: без неё любой вошедший наполнял бы общую
корзину чем угодно, и удалять это было бы некому.

Отдельная забота — не принять за обложку что попало. Open Library на книгу без обложки отвечает
картинкой в девять байт, а Google Books — заглушкой «изображение недоступно», и оба ответа выглядят
как успех. Поэтому у обложки есть нижний и верхний предел размера, проверяется тип содержимого,
а адрес запрашивается ровно такой, какой дал справочник.

**Удаление книги убирает и обложку.** Хранилище ведёт список тех, кто обложку показывает, — как и
для файлов книг, — и убирает картинку, когда список пустеет. Держатель здесь карточка, а не
владелец: у одного человека могут оказаться два издания с одинаковой обложкой, и удаление первого
не должно лишать картинки второе.

Об удалении узнаёт и уточнитель — событием `book.deleted`. Иначе заведённая на книгу задача
дождалась бы своей очереди и потратила запрос к справочнику на то, чего уже нет; при суточной квоте
в тысячу запросов это заметно. Он же убирает обложку в редком случае, когда книгу удалили, пока
справочник думал, и картинка приехала к несуществующей карточке: владелец её уже не отпустит —
карточки нет, — а тот, кто положил, отпустит.

**Уточнить можно и повторно.** Закрытая задача не значит исчерпанная: справочник мог не знать
книгу вчера и узнать сегодня, мог ответить не тем, а мог быть недоступен ровно в те попытки, что
ему отвели. На карточке есть кнопка «Уточнить заново» — она возвращает книгу в очередь и заодно
забывает прошлый ответ справочника о ней, иначе спрашивать было бы некого. Стоящую в очереди книгу
повторная просьба не трогает.

Если первый справочник ответил неполно, второй спрашивается ради недостающего — издательства,
ISBN, обложки. Название и авторов при этом не переписывают: их задаёт тот, кто ответил первым,
иначе карточка соберётся из двух разных изданий. Полный ответ закрывает вопрос сразу: следующего
никто не тревожит, суточная квота не бесконечна.

**Расписание живёт в базе, а не в очереди.** Событие о новой книге лишь заводит задачу; когда её
спрашивать, решает фоновый работник. Ждать приходится часами — суточная квота кончается за сотню
книг, — и держать это ожидание в потребителе Kafka нельзя: он занимает партицию, и за одной книгой
встают все следующие. Ответы справочников запоминаются, включая отрицательные: «этой книги здесь
нет» — такой же ответ, и переспрашивать его назавтра значит потратить квоту впустую.

## Интерфейс

Пять страниц: каталог с поиском и отбором, карточка книги, загрузка, полка с подборками, выгрузка.
Обычные HTML, CSS и JavaScript — ни сборки, ни зависимостей: страниц пять, один файл стилей и один
общий скрипт, и любой сборщик здесь весил бы больше, чем весь код.

Страницы отдаёт nginx, а вход обеспечивает шлюз: браузер входит через Keycloak и получает cookie,
недоступную скриптам, после чего шлюз сам прикладывает токен к каждому запросу. Поэтому в коде
страниц нет ни токенов, ни их обновления, ни отдельной страницы входа — есть только разметка и
обращения к API.

**Учётная запись заводится самим читателем**: на странице входа Keycloak есть ссылка
«Регистрация», и после заполнения формы человек сразу оказывается в своей — пустой —
библиотеке. Страницы входа и регистрации показываются по-русски: в realm включены русская и
английская локали, русская выбрана по умолчанию, переключатель языка остаётся на форме. Ни администратор, ни отдельная страница регистрации для этого не нужны; смена пароля
и восстановление доступа — там же, на страницах Keycloak.

Обращения к API шлюз при отсутствии сессии обрывает отказом, а не переводом на страницу входа
(`api_routes`): человека, открывающего страницу, вести на вход правильно, а запрос из скрипта ждёт
данных, и разметка формы приехала бы к нему как «успешный» ответ.

Светлая и тёмная темы переключаются по настройке системы: цвета вынесены в переменные CSS, вёрстка
одна на обе.

Отбор в каталоге виден в адресе страницы — такой ссылкой можно поделиться или вернуться к ней
позже. Постраничность работает курсором, как и в API: номера страницы у каталога нет вовсе.

## Локальный стенд

```bash
cd deploy/compose && cp .env.example .env && docker compose up -d
```

Поднимаются PostgreSQL, Kafka, SeaweedFS, Keycloak, oauth2-proxy, Valkey,
Prometheus и Grafana — всё окружение сервисов. Сами сервисы поднимаются
профилем `--profile services` после `./gradlew assemble`.
Подробности, адреса и учётные записи — в `deploy/compose/README.md`.

## Выкат в Kubernetes

```bash
./gradlew assemble && deploy/docker/build-images.sh   # образы
deploy/kind/up.sh                                     # кластер и установка
```

Устроено это тремя слоями, и слои не случайны.

**Операторы и шлюз** ставятся первыми, отдельными релизами: они кластерные, живут в своих
пространствах имён и переживают переустановку приложения. База и очередь ведутся операторами —
CloudNativePG и Strimzi, — как это и делают в промышленных окружениях: оператор умеет то, ради
чего база в кластере и заводится, то есть переключение при отказе, резервные копии и обновление
версии без простоя.

**Платформа** — зонтичный чарт `deploy/helm/platform`: он собирает чужие чарты (Valkey, Keycloak,
oauth2-proxy, SeaweedFS, Prometheus, Grafana, Tempo) и добавляет свои объекты — базу, очередь, топики,
шлюз и секреты. Всё взято у самих проектов: чарты Bitnami, которыми такое ставят по привычке,
с августа 2025 указывают на образы, закрытые для публичного скачивания.

**Сервисы** — пять отдельных релизов одного чарта `deploy/helm/service` с файлом значений на
каждый. Зонтика над ними нет намеренно: единицей выката и отката должен быть сервис, а не
приложение целиком.

Снаружи открыт один адрес. Маршрут ведёт на шлюз входа, а тот уже решает, пускать ли дальше;
Keycloak доступен по тому же адресу, потому что издатель в токене — это адрес, по которому токен
выдан, и он обязан совпадать с тем, что проверяют сервисы. Обложки наружу не выставлены вовсе:
их забирает каталог изнутри кластера, проверив, чья книга.

Сетевые политики описывают, кто с кем разговаривает: к сервису обращается только шлюз входа
(и storage — ещё три сервиса), наружу ходит один уточнитель. Политики действуют не везде
одинаково: их исполняет сетевой слой кластера, и, например, в Docker Desktop они создадутся,
но ничего не ограничат.

**База заводится с раскладкой символов `C.UTF-8`**, и это не мелочь: оператор по умолчанию
создаёт её с локалью `C`, а в ней PostgreSQL не приводит кириллицу к нижнему регистру. Поиск
при этом продолжает работать — но только для слов, написанных так же, как в названии: «книга»
находит, «Проверочная» находит, «проверочная» нет. На стенде с compose база заводится с UTF-8,
поэтому расхождение видно только в кластере.

## Что видно снаружи

Каждый сервис отдаёт три вещи: пробы готовности и живости, метрики для Prometheus и журнал.
Порт для них отдельный (8081) и наружу не выставлен — состояние внутренностей не должно быть
доступно вместе с приложением.

Кроме обычных показателей (запросы, пул соединений, память, потребление очереди) сервисы считают
то, что относится к самой библиотеке:

| Показатель | О чём говорит |
| --- | --- |
| `bookcase_ingestion_parse_seconds` (формат, исход) | Сколько занимает разбор и часто ли карточка выходит неполной. Разделение по форматам обязательно: PDF со сканами и небольшой FB2 отличаются на порядок, в общем среднем это различие пропадает. |
| `bookcase_storage_uploads_total` (исход) | Доля повторных файлов: сколько загрузок закончилось ссылкой на уже лежащий файл вместо копии. |
| `bookcase_storage_upload_size_bytes` | Распределение размеров — по нему видно, когда пора думать о месте. |
| `bookcase_books` (состояние) | Размер библиотеки и сколько карточек ждёт правки руками. |
| `bookcase_enricher_lookups_total` (справочник, исход) | Расход суточной квоты и польза от него: сколько ответов пригодилось, сколько кандидатов отвергнуто как чужая книга. |
| `bookcase_enricher_cache_total` (справочник, исход) | Доля попаданий в память — прямая мера сэкономленной квоты. |
| `bookcase_enrichment_tasks` (состояние) | Очередь уточнения. Растущее ожидание при исчерпанной квоте — обычное дело, растущее число безнадёжных означает, что справочник недоступен всерьёз. |

Два готовых дашборда лежат в `deploy/helm/platform/files/dashboards`: «сервисы» — состояние
и нагрузка по каждому, «путь книги» — воронка от загруженного файла до готовой карточки. Файл
один на оба окружения: стенд подключает его томом, кластер — картой настроек с меткой
`grafana_dashboard`. Лежит он внутри чарта потому, что Helm читает файлы только из своего
каталога, а две копии одного дашборда разъезжаются молча.

Чтобы дашборд работал в обоих местах, метку сервиса проставляет сам сервис, а не сбор метрик:
в стенде цели перечислены вручную и метку можно было бы приписать там, но в кластере цели
находятся сами, и приписывать её негде.

Доли времени считаются по делениям гистограммы, а не готовыми числами из процесса. Разница не
косметическая: доли, посчитанные внутри одного экземпляра, нельзя сложить с долями другого —
среднее от двух 95-х долей не равно 95-й доле, — а деления складываются. Заодно к делениям
прикрепляются примеры: у точки на графике есть идентификатор трассы, и из всплеска открывается
тот самый запрос, который в него попал.

Журнал печатается строками текста при разработке и структурой ECS в кластере — переключается
переменной `LOG_FORMAT`, разбирать текст регулярными выражениями не приходится. В каждой записи
есть идентификатор запроса, и он не теряется на очереди: наблюдение включено и у отправителя, и у
получателя, поэтому путь одной книги через ingester → catalog → enricher читается по одному
идентификатору, хотя проходит через три сервиса и две передачи через Kafka.

Тот же идентификатор — ключ к трассе. Трассы собирает Tempo, он есть и на стенде, и в кластере;
сервисы отправляют их по OTLP. Связка — OpenTelemetry: это то, на чём сегодня сходится отрасль,
её протокол понимают все приёмники. Micrometer поддерживает и Brave, но на проводах формат один
и тот же (заголовок W3C `traceparent`), так что выбор ни к чему не привязывает.

Адрес приёмника задаёт окружение, и это не мелочь: без адреса отправитель не создаётся вовсе.
Поэтому запуск из среды разработки и автоматические проверки не стучатся никуда и не ждут
таймаутов, а идентификатор в журнале остаётся на месте. По той же причине сервисы не связаны
с Tempo зависимостью запуска: сбор трасс не должен решать, поднимется приложение или нет.

```
путь 6a824f581d5cad47…
  ingester  заведена задача разбора 14bc8427-e375-4cbe-92fc-2fa459c0a30d
  ingester  файл d406e4e95d540bb6… разобран, формат EPUB
  catalog   книга a765af85-8b37-4146-8cf3-c0fc7a340328 добавлена в библиотеку
  enricher  книга a765af85-8b37-4146-8cf3-c0fc7a340328 поставлена в очередь уточнения
```

## Безопасность

Разграничение здесь построено не на ролях, а на владении: `owner_id` берётся только из
проверенного токена, никогда из тела запроса, и на чужую книгу сервис отвечает 404 — тем же, чем
на несуществующую. Это правило держит и поиск, и скачивание, и обложки, и удаление.

Каждый сервис проверяет токен сам — подпись по ключам издателя, издателя, получателя и срок.
Шлюз перед ними ничего из этого не заменяет: то, что он проставляет в заголовки, для сервиса
обычные данные от клиента.

От подделки межсайтовых запросов защищают три вещи сразу. Cookie сессии выдаётся с признаком
`SameSite`, поэтому браузер не приложит её к запросу, начатому чужим сайтом. Сервисы работают по
токену, а не по cookie, — заголовок с токеном чужая страница проставить не может. И, наконец,
изменяющие запросы проверяются по заголовку источника: пришёл с чужой страницы — отказ, пришёл без
источника (программный клиент) — проходит, потому что подделка ему не грозит.

Страницы отдаются с политикой содержимого: браузеру разрешено выполнять только наши файлы и
обращаться только к нам. Ради этого код страниц вынесен из разметки в отдельные файлы, а встроенные
стили заменены классами — разрешение `unsafe-inline` свело бы защиту на нет. Первый рубеж против
чужого кода всё равно остаётся прежним: весь вывод экранируется, потому что названия и авторы
приходят из чужих файлов.

Книги всегда отдаются потоком байтов с запретом угадывать тип содержимого: «книга» с разметкой
внутри не должна исполниться в браузере как страница.

**Чего на стенде нет и что обязательно в настоящем окружении.** Стенд работает по http, поэтому
cookie сессии выдаётся без признака «только по защищённому соединению». В рабочем окружении нужны
TLS на шлюзе (у `Gateway` — слушатель `HTTPS` с сертификатом), `cookie_secure = true` у шлюза входа
и внешний адрес на `https://` — он же попадёт в токены как издатель. Кроме того, стоит ограничить
частоту запросов на входе: от перебора паролей защищает Keycloak, а вот поток запросов к API
сейчас ничем не ограничен.

## Проверки

Кроме тестов и анализаторов, которые входят в обычную сборку, есть три проверки, которые
запускаются отдельно: они смотрят не на код, а на то, что из него получается, — состав
зависимостей, образы, манифесты и работающая система целиком.

### Уязвимости и настройки: `tools/scan.sh`

```bash
tools/scan.sh deps      # зависимости по перечню состава (SBOM)
tools/scan.sh repo      # секреты и настройки в файлах репозитория
tools/scan.sh charts    # собранные манифесты: kube-linter и trivy
tools/scan.sh images    # собранные образы
tools/scan.sh           # всё подряд
```

Перечень состава строит сам Gradle (`./gradlew sbom`) и заново при каждом запуске — список
«библиотека → версия», который не может устареть, в отличие от файла с зафиксированными версиями.
Он же уезжает внутрь образа: Spring Boot кладёт его в `META-INF/sbom`.

Каждый шаг сначала пишет полный отчёт в `build/reports/quality`, а потом отдельно проверяет,
не осталось ли в нём находок важности HIGH и выше. Отчёт остаётся полным — с находками любой
важности и с подавленными, — потому что «зелено» и «зелено, потому что всё подавлено» должны
различаться на глаз.

Принятые риски живут в `.trivyignore.yaml`, и у каждого есть три вещи: что подавлено, почему это
неопасно здесь и до какого числа решение действует. По истечении срока находка снова роняет
проверку.

Версии, которыми управляют спецификации зависимостей (Spring Boot, AWS SDK), при этом не
переопределяются, даже когда исправленная версия уже вышла: переопределение вынимает одну
библиотеку из проверенного набора и делает сборку не тем, что выпускали авторы спецификации.
Вместо этого разбирается, достижим ли уязвимый путь, — и обычно оказывается, что нет: у lz4 не
включено сжатие, у log4j нет ядра с разметками вывода, у Netty не создаётся асинхронный клиент.

С образами наоборот: там уязвимости приходят из пакетов базового слоя, и лечатся они пересборкой.
Ворота по образам роняют сборку только на том, для чего исправление существует: держать проверку
красной из-за того, что починить нечем, — верный способ перестать ей верить.

### Манифесты: kube-linter

Проверяются собранные `helm template` манифесты — то, что действительно уедет в кластер с нашими
значениями, а не значения по умолчанию. Наборы правил два, и это важно:

- `config/kube-linter/services.yaml` — собственные сервисы, полный набор без исключений;
- `config/kube-linter/platform.yaml` — чужие чарты, без двух правил о том, как их образы
  запускаются внутри (файловая система только для чтения и запуск не от root). Через значения
  чартов это не задаётся, а править чужие шаблоны означало бы проверять каждый компонент заново.

Всё, что задаётся значениями, приведено в порядок: пределы ресурсов у всех частей платформы
(у SeaweedFS их не было вовсе), права Grafana ограничены своим пространством имён вместо
кластерных, описание realm вынесено из карты настроек в секрет — в нём лежат секреты клиентов.

### SonarQube

Сервер поднимается рядом на время прогона:

```bash
docker compose -f tools/sonar/compose.yaml up -d
SONAR_HOST_URL=http://localhost:9000 SONAR_TOKEN=... ./gradlew sonar
```

Разбор идёт по всем модулям и по страницам: Java, HTML, CSS и JavaScript. Плагин сам передаёт
сканеру исходники, скомпилированные классы и весь classpath зависимостей — classpath нужен
не для поиска уязвимостей в чужих библиотеках (это дело Trivy), а чтобы разбирать типы в нашем
коде: без него правила, которым нужно знать сигнатуры, молча не срабатывают. Отчёты checkstyle,
SpotBugs и покрытия приезжают туда же готовыми.

Что нашлось и что с этим сделано: незакрытый архив при отказе в разборе FB2, потерянный откат
при ошибке ввода-вывода во время загрузки файла (проверяемое исключение Spring по умолчанию
не откатывает), безразличие к регистру только для латиницы в выражении, которое чистит русские
названия, поля ввода без подписи на трёх страницах, два атрибута `class` у одного тега, время
без указания часового пояса, устаревшие вызовы. Осталось 47 замечаний, ни одного дефекта
и ни одной уязвимости; оценки — A по надёжности, безопасности и сопровождаемости, покрытие 69 %.

Шесть замечаний о безопасности разобраны и приняты с обоснованием прямо в Sonar: отключение
защиты от подделки межсайтовых запросов там, где нет сессии и cookie; временные файлы, которые
создаются со случайным именем и правами только для владельца; запрос каталога, который собирается
из имён столбцов, заданных в коде, а всё пользовательское уходит именованными параметрами.

Остальные 47 — стилистические: повторяющиеся строки (имена параметров в SQL), сложность
выражений разбора имён файлов, ожидание `await` на верхнем уровне (для него страницы пришлось бы
переводить в модули).

### Запросы к работающей системе: коллекция Postman

`docs/postman/bookcase.postman_collection.json` проходит путь книги целиком — загрузка файла,
разбор, появление карточки в каталоге, правка, полка, ссылка на скачивание и скачивание по ней,
выгрузка библиотеки — и проверяет отказы: чужая книга и чужой файл (404, а не 403 — библиотека
личная), просроченный токен, токен, выписанный другому получателю, запрос без токена и ссылка
с испорченной подписью.

```bash
docker compose -f deploy/compose/compose.yaml --profile services up -d
newman run docs/postman/bookcase.postman_collection.json \
    -e docs/postman/local.postman_environment.json --working-dir docs/postman
```

Учётные записи и клиенты для этого заведены в описании realm и существуют только на стенде:
`bookcase-test` меняет логин на токен напрямую, `bookcase-foreign` выдаёт токен без нужного
получателя, `bookcase-expiring` — токен со сроком жизни в одну секунду (иначе просроченного
пришлось бы ждать пять минут).

## Стиль кода

Раскладку кода — отступы, переносы, положение скобок — задаёт форматтер
google-java-format в режиме AOSP, подключённый через Spotless. Обсуждать её не нужно
и нельзя: `spotlessApply` переписывает файл машинально. Ширина строки — 100 колонок,
отступ — четыре пробела.

Checkstyle занимается тем, что нельзя исправить, не понимая смысла кода: имена, размеры
методов, видимость полей, javadoc на публичных типах. Правила о пробелах и скобках в наборе
тоже есть, но при работающем форматтере они не срабатывают — это барьер на случай правки
в обход сборки.

`spotlessCheck` входит в обычную `check`: репозиторий отформатирован с первого коммита,
и держать формат отдельным необязательным этапом незачем.

Исключения анализаторов складываются из двух слоёв. Общие для всего репозитория:

```
config/spotbugs/exclude.xml
config/checkstyle/suppressions.xml
```

Собственные исключения модуля кладутся рядом с ним и добавляются к общим, а не заменяют их:

```
services/<сервис>/config/spotbugs/exclude.xml
services/<сервис>/config/checkstyle/suppressions.xml
```

Единичные случаи закрываются в коде — `@SuppressFBWarnings` с обязательным обоснованием,
`@SuppressWarnings("checkstyle:ИмяПравила")` на объявлении или пара комментариев
`// CHECKSTYLE.OFF: ИмяПравила` … `// CHECKSTYLE.ON: ИмяПравила` по месту.
